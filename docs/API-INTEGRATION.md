# Web API Integration

The web application consumes the Autrifix backend.

## Contract rule

Backend API specifications are authoritative for server contracts.

If the frontend needs a new field or endpoint:

1. identify the backend requirement;
2. update/verify the backend spec;
3. implement the backend contract;
4. update the web integration;
5. test both sides where appropriate.

Do not silently depend on undocumented response fields.

## Error mapping

The frontend should translate backend errors into useful user-facing messages while preserving enough detail for debugging in development.

## Authentication

Use the authentication mechanism already established in the project.

Do not store credentials/tokens insecurely merely to simplify client access.

## Generated types (ADR-003)

**Do not hand-write API types.** The backend's OpenAPI schema is the source of truth.

```
npm run api:gen      # export schema from the backend, then regenerate types
npm run api:schema   # export only  -> openapi/schema.yml
npm run api:types    # generate only -> lib/api-types.ts
npm run typecheck    # tsc --noEmit
```

| File | Edit by hand? | What it is |
|---|---|---|
| `openapi/schema.yml` | **No** | Exported from drf-spectacular |
| `lib/api-types.ts` | **No** | Generated by `openapi-typescript` |
| `lib/api-schema.ts` | Yes | Aliases, `unwrapList`, `jobStatusLabel` |
| `services/*.ts` | Yes | Thin call wrappers, typed from the above |

**Run `api:gen` after any backend contract change.** Forgetting it reproduces exactly the
drift ADR-003 exists to prevent — stale types that typecheck cleanly and fail at runtime.

Read and write shapes differ. `ServiceRequest.category` is the full category object coming
back and a bare UUID going in, so writes use `ServiceRequestInput`, not `Partial<ServiceRequest>`.

### When the generated types look wrong

They may be right and the backend annotation wrong. `ServiceRequest.category` was documented
as a UUID while the API returned an object, because `to_representation` bypassed the declared
field. **Fix the backend annotation, do not cast around it here** — the whole value of
generation is that the schema can be trusted.

## Backend behaviour the client must respect

- **Completion is two-sided.** A provider records `final_amount` and the job moves to
  `awaiting_confirmation`; only the customer can then set `completed`. A provider sending
  `completed` gets `409`.
- **Discovery coordinates are approximate.** Providers below the exact-location verification
  level see customer coordinates snapped to a ~1 km grid, with `distance_km` derived from the
  snapped point.
- **`403 verification_required`** on accept carries `current_level`, `required_level`, and
  `verification_url` — route the provider there rather than showing a generic error.
- **`409` on accept** means claimed, expired, or at the concurrent-job cap. **`409` on request
  creation** means the customer is at their open-request cap. These are ordinary outcomes and
  need real messages, not a crash.
- **`role` is read-only after signup.** See CONFLICT-W001-A.

## CI enforcement

`.github/workflows/ci.yml` runs two jobs:

1. **check** — typecheck, lint, test, build.
2. **api-contract** — regenerates `lib/api-types.ts` from the committed `openapi/schema.yml`
   and fails if they differ.

The second job matters for this document. ADR-003 turns backend drift into a compile error,
but only while the types match the schema; a stale `api-types.ts` typechecks perfectly and
lies exactly as the hand-written types did.

It uses `git add --intent-to-add` first, so an untracked generated file counts as drift too —
otherwise `git diff` ignores untracked paths and the check passes vacuously.

### What CI cannot check

**Whether `openapi/schema.yml` is current with the live backend.** The backend is a separate
GitHub repository (`Autrifix-be`), so verifying that from here would need cross-repo
credentials. CI catches *types-vs-schema* drift; only running `npm run api:gen` against a
backend catches *schema-vs-backend* drift.

In practice that means: **run `npm run api:gen` after any backend contract change and commit
the result.** If it is forgotten, the failure is silent in exactly the way this whole
arrangement exists to prevent — which is worth knowing rather than assuming CI has it covered.
